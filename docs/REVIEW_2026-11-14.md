# 复核：2026-11-14 那笔改动（96c2ced）

复核对象：`96c2ced fix: isolate Site credentials and preserve verified collection progress`
方法：读 diff、跑它的 54 个测试、再用真实公开快照 `/api/data` 交叉验证。
结论：**安全与契约方向是对的，但把「不敢声称成功」做成了「系统永远成功不了」**——队列在结构性赤字下运行，而随附的调度示例根本触发不了出刊轮。

---

## P0-1 随附调度永远不会跑出刊轮（已修）

**现象**：`ops/cron`、`ops/launchd`、`ops/systemd` 三处示例都直接调用 `src/cli.mjs run`，不传 `--scheduled-for`；而 `isEditionRound(null)` 返回 `false`。

**叠加**：`isEditionRound` 从「±45 分钟容差」改成了 `minutes === 600` 精确匹配。cron 启动抖动 40 秒、机器刚从睡眠唤醒、Node 冷启动，都会让 10:00 那轮变成补采轮。

**线上证据**：70 个目标里 40 个的 `windowTo` 停在 `2026-11-14T02:0x`（北京 10:00）那一轮，之后 04/06/08/14 各只有 5–8 个。也就是说，只有**手工/特殊调用**跑过一次全量，调度本身从未跑过出刊轮。

**已修**：新增 `ops/run-scheduled.mjs`，从 `config/policy.json` 的 `schedule.rounds` 反推「当前属于哪个计划时段」，把该时刻作为 `--scheduled-for` 传入；10:00:41 启动仍然算 10:00 那轮。三个 ops 示例已改为调用它。

## P0-2 容量赤字：52/61 个可检查目标过期（部分修复，需决策）

**实测**（`node src/cli.mjs audit`）：

```
新鲜度：<4h 8 · 4-8h 5 · >8h 48 · 过期 52     最久 15.4h（carl/GitHub）
容量：每天可检查 156 次 / 需要 366 次 → 结构性赤字
```

算法：61 个可检查目标 × 24h ÷ 4h 重到期 = 366 次/天；7 轮补采 × 8 + 出刊 100 = 156 次/天。

**叠加**：`effectiveCap = edition ? targets.length : Math.min(cap ?? 8, 8)` 把 `--cap` 硬压到 8，连手工清积压都做不到；而 `ops/cron` 里那行 `--cap 100` 因此完全无效。

**已修**：`--cap` 现在生效（默认仍是 8，硬上限 40，防止误写成长跑）。新增 `resolveRoundCap()` 与测试。

**仍需你决策**（三选一，选完我可以直接改）：
1. `success` 重到期从 4h 放宽到 **≥10h**（`SUCCESS_RE_DUE_HOURS`）；
2. 补采轮容量提到 **≥38**（会拉长单轮到 25–30 分钟）；
3. 按主/次平台分层：主平台 4h、次平台 24h（推荐，最贴近「日更作者当天发现」的真实需求）。

## P1-3 写回确认会死锁（已修）

`batchApplied()` 有两处会把「站点其实存了」判成「没存」：

- `Date.parse(remote.contentCheckedAt) >= ...`：公开镜像的 post 里**没有** `contentCheckedAt` 字段（只有 `contentStatus`/`contentFailCount`），`Date.parse(undefined)` = NaN，比较恒为 false；
- `remote.evidence === post.evidence`：站点存 `fulltext`、我们推 `transcript` 也会判 false。

后果：`flushBatch` 判失败 → `pendingCollectionBatches` 保留 → **下一轮开头 replay 抛错，整轮中止**（`throw new CollectError('待重放批次未获明确成功…')`），而且不会自愈，只能手改 `state.json`。

**已修**：证据按「是否拿到正文」分级比较（`transcript`/`fulltext`/`visual` 同级），缺失 `contentCheckedAt` 视为「回读无法回答」而不是「未应用」。两条回归测试锁住。

## P1-4 失败轮次没有账本记录（已修）

队列读取失败时直接 `throw`，而 `ledger.finish()` 只在正常路径调用。于是**恰好是最需要记录的失败轮**在 `state/runs/` 里不存在——3 天验收表会显示「每天都在跑」。

**已修**：`catch` 分支写 `status: 'failed'` + `finish()` 后再抛出。

## P1-5 21 个目标永远不可能成功，却一直排队（未改，需决策）

`gated.mjs` 现在恒定 `status:'retry'` 且 `posts: []`（线索只落到 evidence JSON）。这条本身符合「不伪造成功」，但状态选错了：抖音/小红书/微博在没有授权会话时，重试一百次结果一样。

- 21 个目标 × 每 2–24h 重入队 ≈ 每天 50 次检查，全部消耗在必然失败上；
- 每轮只有 8 个名额（现在可提到 40），它们会挤掉本来能出结果的 B站/RSS；
- 更糟的是它把「缺授权」伪装成「下次会好」，`needsAttention` 面板永远看不到这块缺口。

**建议**：改 `blocked` + `code: 'NEEDS_SESSION'` + `nextStep`，并保留 `leads` 证据文件；确有会话时再手工解锁。要不要我改，一句话的事。

## P1-6 B站的「覆盖边界」判定会误杀高频账号（未改，需决策）

```js
const boundaryReached = nonPinnedDates.some(date => date <= new Date(windowFrom).getTime());
result.status = !metadataFailed && ordered && boundaryReached ? 'success' : 'retry';
```

- 只核验 6 条候选；7 天内发了 7 条以上的账号，这 6 条全在窗口内 → `boundaryReached=false` → **永久 retry**；
- `metadataFailed` 在任一条 `view` 接口失败时置真。一个已删除/私密视频会让整个账号永远停在 retry（不是阻塞，是永久）。

**建议**：`boundaryReached` 补一个分支——`nonPinnedDates.length < maxEnrich` 时说明「列表已到底」，视为已覆盖；`fetchVideoMeta` 区分 `-404/-62004`（已删除，跳过但不影响整轮）与瞬时错误。

## P1-7 空字幕轨从 blocked 改成 retry，内容队列被无解任务占满（未改，需决策）

线上 18 条 B站 post **全部**是 `metadata`，内容队列里 35 条 `pending`、15 条 `verified`——也就是说「官方字幕为空」是这批视频的常态，不是偶发。

每条无字幕视频都会按 2/4/8/16/24h 反复尝试，每轮占 4 个正文名额中的一部分，把真正能拿到正文的 RSS 挤掉。

**建议**：同一 post 连续 3 次「字幕轨为空」后转 `blocked`，`nextStep='需要 ASR 或人工转录'`。注意我加的 `sameCauseCount` 升级只作用于目标状态，不作用于 contentAttempt，所以这条得单独补。

## P2 记录自相矛盾（RSS）

`rss.mjs` 里 `hasBody` 被硬编码成 `false`，但 evidenceNote 的三元表达式仍按 `hasBody` 分支：

```js
hasBody ? `自带正文（N 字），已按原文入库` : `仅提供摘要（N 字），正文未取得`
```

结果：明明已经把 5000 字 feed 全文写进 `evidenceFile`，note 却写「正文未取得」。同一行记录里自相矛盾。修法：note 改成「已存 feed 文本 N 字，未复核为完整正文」。
