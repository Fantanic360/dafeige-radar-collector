# 容量评估（CAPACITY）

结论先给：**70 个目标、单执行者、一轮全量约 15–25 分钟**，能塞进现有的 22 分钟轮次预算，但**没有余量**。所以非 10:00 轮必须限量，10:00 轮才全量。

数据来源：本机 macOS（Apple Silicon）、Chrome 157 headless、家庭宽带、`config/sources.json` 的 68 个入口 + 2 个补充目标。测法：`node src/cli.mjs run --force --cap 100`，从 `state/runs/*.json` 的 `targets[].durationMs` 读实际耗时。

## 1. 单目标实测耗时

| 目标类型 | 典型耗时 | 主要成本 | 说明 |
|---|---|---|---|
| RSS（有 feed） | 1–3 s | 一次 HTTP + 解析 | 最快的来源 |
| GitHub（pin 仓库） | 2–4 s | releases API | 匿名限额足够 |
| 小宇宙 | 2–4 s | 一次页面 + 解析 `__NEXT_DATA__` | |
| B站 | 18–30 s | 渲染列表 10–15 s + 每条候选 2 次 API | 17 个入口，是主要耗时来源 |
| 抖音/小红书/微博（可读） | 5–10 s | 渲染 + DOM 提取 | 不可读时 3–6 s 快速判 blocked |
| X / YouTube（本网络不可达） | 6–10 s | 7 秒探测后返回 retry | 加了探测，避免旧版 60–180 s 的空转 |

B站为什么这么贵：列表接口服务端被封（`-352`），只能渲染；渲然后每条候选还要 2 次官方 API（`view` + `player/v2`）。已把每条目标的候选条数压到 6 条，只对落在窗口内的作品取字幕。

## 2. 一轮的预算分配

| 轮次 | 目标上限 | 预计耗时 | 说明 |
|---|---|---|---|
| 10:00 出刊轮 | 全部（≤100） | 15–25 min | 必须覆盖全部启用作者 |
| 其他 7 轮 | 8 | 1.5–4 min | 「从未检查 → 主平台 → 最久未查」，按平台交错 |

70 个目标 ÷ 8 = 每约 2 小时一轮 × 7 轮 + 1 次全量 ≈ **每 24 小时覆盖全部目标 2 次以上**；对「日更作者新作当天可发现」足够，对「小时级追更」不够——这是刻意的取舍，不是能力上限。

## 3. 公平性：怎么保证不只有少数平台被查

1. **排序**：从未检查过的优先；其次主平台；再次按 `nextDueAt` 最久未查。
2. **交错**：按平台分道，轮流取一个，避免 B站 17 个目标把 8 个名额全占。
3. **失败熔断**：同一主机连续失败 2 次，本轮剩余目标直接标 retry 并写明「未做任何读取」，把预算留给能读的平台。
4. **超时保护**：单目标 120 s 硬超时；超时后重置浏览器实例，避免下一目标继承卡死的标签页。

## 4. 什么时候该扩容

出现以下任一情况，说明单执行者不够，应拆成 2–3 个执行者（按平台分道）或加机器：

- 10:00 轮常态超过 25 分钟；
- `deferred`（本轮没排上的目标）持续 > 20；
- 某个平台的 `nextDueAt` 常年落后实际时间 6 小时以上。

拆分方式：用 `--only` 按来源分组，各自带一份 `RADAR_STATE_DIR`；站点侧打上 `integration/site` 的租约补丁后，多执行者也可共享同一队列。

## 5. 不要做的事

- 不要把所有检查时间刷新成当前时间（交接包里明确点名的错误做法）。
- 不要为了「覆盖」把 `success` 写成不实状态；宁可 `retry`。
- 不要在同一轮里既全量出刊又补正文；正文队列默认 4 条/轮，多了会把主列表挤掉。
